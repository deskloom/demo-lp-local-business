CASE NOTE

このLPの作り方

見た目を整えるだけでなく、「問い合わせが増えたか」を数字で確かめ、改善を続けられるところまでを1ページに組み込みました。導線・計測・AI検索への対応・品質確認の4つに分けて説明します。

  • 1. 問い合わせへの導線
  • 2. 計測の設計（GA4 / GTM）
  • 3. AI検索（AIO）・SEO
  • 4. 品質の数字

01

問い合わせへの導線

読む人が「予約しよう」と思った瞬間に、どこにいてもボタンが手の届くところにあるようにしました。

  • 予約・電話の入口を5か所に配置：ヘッダー、ファーストビュー（Web予約と電話の2択）、アクセス欄の電話番号、予約欄の電話番号、スマホの画面下の固定ボタン。
  • スマホの固定ボタンは、予約フォームが見えたら自動で隠す：フォームの入力をじゃましないため。
  • 不安を先に消す順番：お悩み → 大切にしていること → 施術の流れ → 料金 → お客様の声 → 院長 → よくある質問 → アクセス → 予約。「何をされるのか」「いくらかかるのか」「無理に通わされないか」に、予約の前に答えています。
  • フォームは入力を最小限に：電話かメールのどちらか1つでよく、入力ミスはその場で欄の下に表示。確認画面のあとに入力が変わったら確認を取り消し、送信内容のずれを防ぎます。

02

計測の設計（GA4 / GTM）

ページの中の動きを、Googleタグマネージャー（GTM）が読み取れる dataLayer にイベントとして積んでいます。GTMのコンテナを入れれば、そのままGA4のイベントとして集計できます。お名前・電話番号などの入力値は一切送りません。

問い合わせまでの流れと、各段階で記録するイベント

  1. ページを見るpage_viewGA4が自動で記録
  2. どこまで読んだかsection_view
  3. 予約・電話ボタンcta_click
  4. フォーム入力開始form_start
  5. 確認画面へform_confirm
  6. 送信完了form_submit
記録するイベントと、そこから分かること
イベントいつ一緒に送る情報分かること
section_view各セクションが画面の中央に0.8秒以上留まったとき（1回だけ。ボタンで一気に通り過ぎた分は数えない）section（どのセクションか）どこで読むのをやめているか
cta_click予約・電話ボタンを押したときcta_location（header / hero / sticky / access / reserve）、cta_type（web / tel）どの位置のボタンが効いているか、Webと電話のどちらが選ばれているか
form_startフォームに最初に入力したときなしフォームまで来た人のうち、書き始めた人の割合
form_error入力ミスで先に進めなかったときerror_fields（どの欄か）どの入力欄でつまずいているか
form_confirm確認画面に進んだときなし入力を終えた人の数
form_submit送信が完了したときmode（live / demo）問い合わせ数そのもの（最重要の指標）

この数字で見る指標の例

  • 問い合わせ率 ＝ form_submit ÷ page_view。月の目標件数から、必要な訪問数を逆算できます（例：問い合わせ率1%で月30件なら、月3,000訪問）。
  • ボタンのクリック率 ＝ cta_click ÷ page_view。cta_location 別に見ると、どの位置のボタンを残し・どこを直すべきかが分かります。
  • フォーム完了率 ＝ form_submit ÷ form_start。低ければ、form_error の error_fields でつまずいている欄を特定します。
  • 読了の深さ：section_view の減り方で、離脱の多いセクションを見つけて順番や文章を直します。

計測の動きを実際に見るLPを開くと右下に記録されたイベントが表示されます。ボタンを押したり、フォームに入力したりしてみてください。

03

AI検索（AIO）・SEO

ChatGPTやGoogleのAIによる概要などが、ページの内容を正しく読み取り、引用しやすい形に整えています。実際に引用されるかは各サービスの仕様次第なので、ここでは「読み取りやすい構造にしたこと」と「その確かめ方」を書いています。

  • 構造化データ（JSON-LD）：店舗情報（HealthAndBeautyBusiness：住所・営業時間・電話・料金メニュー）と、よくある質問（FAQPage）。
  • FAQの構造化データと、ページに表示しているFAQの一致を自動テストで確認：片方だけ直して食い違う、というよくある事故を防ぎます。
  • 見出しを「質問と答え」の形に：よくある質問は、AIがそのまま回答に使いやすい短い文で書いています。
  • AI向けの要約ファイル：llms.txt（店の概要・料金・営業時間・FAQをMarkdownで要約）。
  • 検索エンジン向けの基本：robots.txt、sitemap.xml、正規URL（canonical）、SNSで共有されたときの画像とタイトル（OGP・1200×630の画像）。
FAQの構造化データの中身を見る 
{
  "@context": "https://schema.org",
  "@type": "FAQPage",
  "mainEntity": [
    {
      "@type": "Question",
      "name": "初めてでも受けられますか？",
      "acceptedAnswer": {
        "@type": "Answer",
        "text": "はい。初回は20分のカウンセリングで…"
      }
    },
    …（全6問）
  ]
}

04

品質の数字

「動いているように見える」ではなく、実際に測った数字です。

  • 96パフォーマンス
  • 100アクセシビリティ
  • 100ベストプラクティス
  • 100SEO
  • Google の Lighthouse 12 でスマホ（モバイル）設定のまま、公開中のこのLPを計測（2026年10月15日）。PC（デスクトップ）設定では4項目すべて100でした。点数は回線などで多少変わります。
  • 自動テスト 45件がすべて通過：入力チェック、送信の流れ、計測イベントの順番（入力値を送っていないことも確認）、ページの構成とAI検索向けファイルの有無。
  • HTMLの文法チェック（html-validate）でエラー0。
  • スマホ（375px）・タブレット（768px）・PC（1280px）の3つの幅で画面を撮って確認し、横にはみ出すスクロールがないことを数値でも確認。
  • 読みやすさ：本文の文字と背景の色の差（コントラスト比）を、アクセシビリティの基準（WCAG AA・4.5:1）以上に。キーボードだけでも操作でき、動きを減らす設定の人には演出を止めます。
  • 軽さ：外部のフォント・画像・ライブラリを読み込まず、イラストはすべてコードで描いています。

本番の店舗サイトにするときは

  • 写真・文章を実際のものに差し替え、GTMのコンテナを設置（計測イベントはこのまま使えます）。
  • 予約フォームの送信先（メール通知・スプレッドシート・予約システムなど）を接続。
  • 公開後、上の指標を見ながら、ボタンの位置・文章・セクションの順番を改善。
